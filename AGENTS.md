# Xray account management fork

Read `docs/xray-account-handoff.md` before project work. It records the user's decisions from the source conversation and distinguishes verified evidence from proposals. Also follow the upstream engineering guidance in `CLAUDE.md` and any applicable nested guidance.

- This is a separate repository from Noctiluca. The first version uses one 3x-ui fork, with account, traffic, and quota functionality organized as modules in this repository.
- First-version requirements: ordinary customer accounts, per-account traffic, and one shared monthly quota. On 2026-09-11 the user explicitly deferred simultaneous-device limits from the first version. Device identification, online slots, and self-service device removal are not first-version deliverables or acceptance blockers.
- Confirmed first-version deployment scale: two proxy servers, approximately 20 customer accounts, and 20 people using the proxy concurrently across the system. These are acceptance targets, not account/device/connection caps. Cross-node account traffic aggregation and shared quota enforcement are first-version requirements; single-node testing alone is insufficient.
- Administrators must be able to select multiple customer accounts in a list and modify their traffic quotas in a batch with immediate effect. Update the shared account quota, preserve recorded usage, and distinguish a saved quota from successful runtime enforcement. Detailed batch-operation defaults are documented in the phase-one design.
- Confirmed rules: automatically restore quota-exhausted accounts when a new period or quota increase leaves available quota, preserve administrator suspensions, count upload plus download at the same multiplier across associated configurations, and label units in the UI. The customer UI includes login, usage and remaining quota, connection configurations, and password changes. Changing a web-login password must not rotate proxy UUIDs; leaked proxy credentials have a separate reset operation.
- The user requires compatibility with v2rayN, v2rayNG, Shadowrocket, and Clash. Do not assume approval to replace these with a custom client. On 2026-09-11 the user approved `docs/superpowers/specs/2026-09-11-xray-account-phase1-design.md`, adopting its defaults: administrator-created accounts, UTC calendar months, integer bytes with GiB display, and batch assignment of a monthly quota for the current and subsequent periods without resetting usage. Do not request this design approval again. Connection enforcement, disconnected-node policy, and credential-reset details still require the validation/refinement explicitly recorded in the design.
- Do not introduce IP, connection, registration, or subscription-download caps as substitutes for the deferred device limit. Stock VLESS credentials and client-reported HWID do not reliably identify physical devices. Preserve existing unrelated proxy settings.
- If device management is resumed later, removing one device must not invalidate every device's configuration. Strict admission and selective termination require a validated connection-path design; a portal-only check is insufficient. First-version quota enforcement still needs verified account-level blocking without disrupting other accounts.
- Reuse existing 3x-ui UI and proxy management. Ordinary customer authentication and server-side authorization are distinct from panel administrator login and proxy client credentials.
- Baseline: v3.7.0, commit f727d04f6522bb94a8fb52e8352fdcafb51c11e1. Known security findings and upstream fix candidates are in the handoff; no fixes have yet been applied in this checkout.
- Do not deploy, expose the panel, run privileged installation scripts, or imply production readiness during setup. Preserve unrelated files and use narrow Git operations.
